# One-Hand Interface

> **Направление:** Arduino & Robotics
> **Дополнительные направления:** Assistive Tech & Протезирование · Accessibility · HCI · Physical Computing
> **Уровень сложности:** Начальный / средний
> **Срок:** 1–2 недели

Физический контроллер, позволяющий одной рукой выполнять набор основных действий на компьютере. Главная задача — спроектировать понятный язык управления большим количеством действий при ограниченном количестве физических элементов.

**Базовый сценарий:** *пользователь → ограничение → нужные действия → модель взаимодействия → аппаратное обеспечение.*

## Проблема

Большинство компьютерных интерфейсов проектируется вокруг стандартного набора устройств: **клавиатура + мышь + две руки.** Но такой способ управления подходит не всем. Человеку может быть сложно одновременно использовать клавиатуру и мышь, нажимать комбинации клавиш или быстро перемещаться между большим количеством элементов управления.

Простое решение «давайте уберём половину кнопок» не работает. Если физических элементов становится меньше, возникает задача:

> **Как сохранить достаточное количество возможностей управления, не превратив интерфейс в набор сложных комбинаций, которые невозможно запомнить?**

## Задача

Создать прототип **One-Hand Interface** — физического контроллера, позволяющего одной рукой выполнять набор основных действий на компьютере.

Например, устройство может состоять из **Joystick + 3 Buttons + Rotary Encoder** и позволять:

* перемещаться по интерфейсу;
* выбирать элементы;
* возвращаться назад;
* прокручивать страницы;
* запускать заданные действия;
* переключаться между режимами.

Главная задача — не собрать контроллер, а **спроектировать понятный язык управления большим количеством действий при ограниченном количестве физических элементов.**

## Сначала пользователь — потом устройство

Принципиально важная часть проекта. Команда не начинает с вопроса «У нас есть Arduino, джойстик и пять кнопок. Что собрать?». Сначала определяется конкретный сценарий и набор необходимых действий:

```text
MOVE
SELECT
BACK
SCROLL
HOME
SWITCH
```

Цепочка:

**User → Limitation → Required Actions → Interaction Model → Hardware**

## Описание

Базовый прототип:

```text
       ┌───────────────┐
       │      ↑        │
       │   ← JOY →     │
       │      ↓        │
       │               │
       │  [A] [B] [C]  │
       │               │
       │     ◉ DIAL     │
       └───────────────┘
```

Одна рука практически не меняет положение. Большой палец работает с джойстиком. Другие пальцы имеют доступ к нескольким большим кнопкам. Рядом находится энкодер.

Например:

**Joystick** → навигация; **A** → выбрать; **B** → назад; **C** → дополнительное действие; **Encoder** → прокрутка.

## Минимальные требования

Первая версия должна:

* управляться одной рукой;
* иметь ограниченное количество физических элементов;
* поддерживать минимум 5 компьютерных действий;
* иметь понятное расположение элементов;
* давать физическую или визуальную обратную связь;
* подключаться к компьютеру;
* преобразовывать физический ввод в цифровые команды;
* не требовать второй руки для основных сценариев;
* иметь хотя бы один законченный пользовательский сценарий.

## Возможное развитие

### Level 2 — Custom Controller

Спроектировать корпус под руку: учитываются расположение пальцев, расстояние между кнопками, размер элементов, сила нажатия, положение запястья, возможность случайного нажатия. Создаётся несколько прототипов корпуса: **Prototype A → Test → Problems → Prototype B**. 3D-печать — инструмент итеративного проектирования.

### Level 3 — Input Mapping

Добавить возможность настраивать действия:

```text
A → ENTER
B → ESC
C → TAB
Encoder → SCROLL
```

Получается: **Physical Input → Mapping → Digital Command**. Один контроллер используется для разных задач.

### Level 4 — Modes

Физических элементов мало, поэтому можно добавить режимы (Navigation, Media, Presentation). Возникает UX-проблема: **как пользователь понимает, в каком режиме находится устройство?** Можно добавить небольшой экран, LED-индикацию, звук, тактильную обратную связь.

### Level 5 — Context Profiles

Вместо ручного переключения — профили:

```text
BROWSER
PRESENTATION
MEDIA
COMMUNICATION
```

Каждый профиль содержит собственный mapping. Пользователь выбирает профиль и устройство перестраивает управление.

### Level 6 — Macro Actions

Одно физическое действие запускает последовательность цифровых действий:

> **Physical Action → Macro → Sequence of Commands**

Здесь Assistive Tech пересекается с автоматизацией.

### Level 7 — POLY Integration

Один из элементов можно назначить для вызова POLY: **Hold A → POLY**. Пользователь удерживает кнопку и говорит запрос. Сочетание двух способов управления:

```text
                 One-Hand Interface
                        │
              ┌─────────┴─────────┐
              ↓                   ↓
       Direct Commands         POLY
              ↓                   ↓
          Computer          AI Actions
```

### Level 8 — Adaptive Interface

Система знает, какие действия пользователь выполняет чаще всего. Интерфейс может **предложить** (не насильно) назначить команду на более удобную кнопку:

> «Ты часто используешь действие X. Назначить его на кнопку C?»

Получается: **Usage Data → Analysis → Recommendation → User Decision → New Mapping**.

## One-Hand Interface + POLY Button

Два разных подхода к Assistive Tech:

- **POLY Button** — максимальное упрощение: *одно действие → AI.*
- **One-Hand Interface** — максимальная функциональность при ограниченном физическом вводе: *несколько элементов → множество действий.*

Их можно объединить, но для MINILAB это самостоятельные проекты с разными инженерными задачами.

## Accessibility Testing

Недостаточно, чтобы разработчик сказал «Мне удобно». Нужно определить критерии:

* количество действий;
* время;
* количество ошибок;
* случайные нажатия;
* необходимость перемещать руку;
* необходимость смотреть на контроллер.

После изменения прототипа тест повторяется: **Prototype → Test → Data → Problem → Redesign → Test**. Это один из главных процессов всего проекта.

## Важное ограничение

One-Hand Interface не должен позиционироваться как универсальное решение для людей с инвалидностью. Корректная постановка:

> **Мы создаём и исследуем альтернативный одноручный интерфейс для конкретного сценария и набора ограничений.**

Урок продуктовой разработки Assistive Tech:

> **Accessibility начинается с понимания конкретного пользователя, а не с предположений разработчика.**

## Оборудование и инструменты

В зависимости от реализации: Arduino/ESP32, joystick, большие кнопки, rotary encoder, небольшой дисплей, LED, вибромотор, провода, 3D-печатный корпус. Конкретный набор участник выбирает **после определения сценария управления**.

## Что предстоит изучить

Physical Computing, микроконтроллеры, Human Interface Devices, обработку кнопок, joystick, rotary encoder, debounce, input mapping, состояния, профили, основы HCI, Accessibility, прототипирование, 3D-моделирование, пользовательское тестирование.

При развитии: **Macros · Usage Analytics · AI Integration**.

## Полученные навыки

Accessibility Engineering, Human–Computer Interaction, Physical Computing, Input Systems, Hardware Prototyping, State Management, User Testing и итеративная разработка физических интерфейсов.

Центральный инженерный навык:

> **умение проектировать интерфейс исходя из возможностей человека, а не возможностей устройства.**

## Результат

Работающий **One-Hand Interface v0.1** — физический контроллер, позволяющий выполнить выбранный набор компьютерных действий одной рукой.

Минимальная цепочка: **Human Action → Physical Input → Controller → Input Mapping → Computer Action**.

## Критерии готовности

Проект завершён, если:

* контроллер действительно можно использовать одной рукой;
* определён конкретный пользовательский сценарий;
* реализовано минимум 5 действий;
* элементы физически доступны без постоянной смены положения руки;
* пользователь получает обратную связь;
* команды корректно передаются компьютеру;
* существует понятная схема управления;
* проведено хотя бы несколько итераций тестирования;
* результаты тестов повлияли на конструкцию или mapping;
* участник способен объяснить, **почему каждый элемент находится именно там и выполняет именно эту функцию**.

## Demo Day

На компьютере открывается заранее подготовленная задача:

> **Открыть презентацию → перейти на третий слайд → прокрутить содержимое → вернуться → вызвать POLY.**

Условие: **можно использовать только одну руку и созданный контроллер.** Участник выполняет весь сценарий, затем показывают первую и вторую версии корпуса и то, как тестирование изменило устройство.
