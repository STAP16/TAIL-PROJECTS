# College Event Manager Agent - Агент управления мероприятиями

**Направление:** AI & Agents
**Дополнительные направления:** Tool Calling · AI Automation · Agentic Systems
**Уровень сложности:** Средний
**Срок:** 2 недели

## Проблема

Информация о мероприятиях колледжа постоянно изменяется.

Появляются новые события, меняются даты и аудитории, мероприятия переносятся или отменяются. При этом работа с системой управления мероприятиями обычно требует вручную открывать интерфейс, искать нужное событие, заполнять формы и изменять необходимые поля.

Для части таких операций естественный язык может быть значительно удобнее.

Вместо последовательности действий в интерфейсе сотрудник мог бы написать:

«Перенеси встречу первокурсников с четверга на пятницу, время оставь прежним».

Но обычной LLM недостаточно. Модель может понять просьбу, однако сама по себе она не умеет безопасно изменять данные системы.

## Задача

Создать специализированного AI-агента для работы с мероприятиями колледжа.

Агент должен понимать запрос пользователя, определять необходимое действие, получать данные через доступные инструменты и при необходимости изменять состояние системы.

Например:

- «Какие мероприятия запланированы на пятницу?»
- «Добавь встречу проектных команд 18 сентября в 16:00».
- «Перенеси День открытых дверей на 12:00».
- «Отмени встречу команды TAIL».

**Ключевая задача проекта** — научиться создавать AI, который не просто генерирует ответ, а выполняет контролируемые действия во внешней системе.

## Описание

College Event Manager Agent работает поверх отдельного источника данных о мероприятиях.

Базовый контур:

`User → Agent → Intent → Tool → Events System → Result → Agent → User`

У агента существует ограниченный набор инструментов. Концептуально:

`find_events()` · `get_event()` · `create_event()` · `update_event()` · `cancel_event()`

При запросе «Что проходит завтра?» агент выбирает инструмент чтения данных. При запросе «Создай встречу TAIL завтра в 15:00» ему уже необходимо: понять намерение; извлечь параметры события; определить, достаточно ли информации; проверить данные; выбрать инструмент; передать корректные аргументы; получить результат операции; сообщить пользователю, что произошло.

**LLM отвечает за понимание намерения и выбор действия. Обычный программный код отвечает за реальное выполнение операции и соблюдение правил системы. Модель решает, какой инструмент использовать. Инструмент выполняет действие.**

## Минимальные требования

Агент должен уметь:

- получать список мероприятий;
- находить мероприятие по пользовательскому запросу;
- получать информацию о конкретном событии;
- создавать новое мероприятие;
- изменять существующее мероприятие;
- отменять мероприятие;
- работать с естественными формулировками пользователя;
- запрашивать недостающую информацию;
- сообщать результат выполненного действия;
- корректно обрабатывать ошибку инструмента.

Минимально должны поддерживаться два типа операций:

- **READ** — получение информации.
- **WRITE** — изменение состояния системы.

## Возможное развитие

**Level 2 — Structured Extraction.** Пользователь отправляет агенту обычный текст объявления: «В среду, 23 сентября, в 14:30 состоится встреча участников чемпионата. Место проведения — актовый зал». Агент самостоятельно превращает текст в структуру: Название → Дата → Время → Место → Категория, и предлагает создать событие. Здесь участник работает со Structured Output и валидацией данных.

**Level 3 — Safe Actions.** Добавить различие между безопасными и изменяющими систему действиями: прочитать мероприятие → можно сразу; найти мероприятия → можно сразу; создать/перенести мероприятие → требуется подтверждение; отменить мероприятие → обязательно требуется подтверждение. Сценарий: пользователь «Отмени встречу TAIL», агент: «Найдена встреча TAIL 18 сентября в 15:00. Подтвердить отмену?». Это вводит важнейшую концепцию: способность агента выполнить действие ещё не означает, что ему следует разрешить выполнять его самостоятельно.

**Level 4 — Conflict Detection.** Перед созданием или переносом мероприятия агент проверяет потенциальные конфликты. Система обнаруживает пересечение по времени и сообщает проблему, предлагая варианты. Здесь появляются Business Rules · Validation · Conflict Resolution.

**Level 5 — College Events Intelligence Integration.** Связать агента с MiniProject [[College Events Intelligence - Мероприятия и аналитика|College Events Intelligence]] из Data & Analytics:

```
                   Sources
                      ↓
          College Events Intelligence
                      ↓
               Events Dataset
                      ↑
                      │
User → Event Manager Agent → Tools
```

College Events Intelligence отвечает за сбор событий, AI Extraction, нормализацию, хранение и аналитику. Event Manager Agent отвечает за понимание запроса, поиск информации, вызов инструментов и управление событиями через естественный язык. Два MiniProject разных Track могут стать частями одной системы.

**Level 6 — Campus Events Integration.** Добавить третий позапроектированный MiniProject — Campus Events из Web Development. Получается цепочка:

```
College Events Intelligence
          ↓
     Events Data
      ↓
Campus Events   Event Manager Agent
      ↓               ↑
   Students         Employee
```

Студент использует Web-интерфейс. Сотрудник управляет системой через AI-агента. Изменение через агента «Перенеси мероприятие на пятницу» меняет данные системы; Campus Events получает обновлённые данные и показывает новую дату. Три команды MINILAB могут создать три независимых компонента одного продукта.

**Level 7 — Event Planning Agent.** Перейти от простого управления к планированию: «Нужно провести Demo Day MINILAB на следующей неделе. Найди подходящее время». Агент получает календарь, анализирует ограничения, ищет варианты, предлагает время, не создавая событие автоматически. После выбора пользователя вызывает инструмент создания. Это полноценный multi-step Agent Workflow.

## Оборудование и инструменты

Специальное оборудование не требуется. Необходимы компьютер, AI-модель/API, тестовая база мероприятий и инструменты разработки.

Для MINILAB агент должен первоначально работать с тестовым или изолированным контуром данных, чтобы ошибочный Tool Call не изменял реальные данные колледжа. Конкретный инженерный стек заранее не задаётся.

## Что предстоит изучить

- устройство AI-агента;
- LLM API;
- Structured Output;
- Function/Tool Calling;
- описание инструментов;
- аргументы инструментов;
- валидация;
- READ и WRITE операции;
- состояние внешней системы;
- обработка ошибок;
- подтверждение действий;
- permissions;
- business rules;
- agent loop;
- взаимодействие AI с обычным программным кодом.

**Главная концепция проекта:** AI-агент — это не просто LLM с хорошим системным промптом. Модель получает возможность взаимодействовать с внешним миром через программные инструменты. Но реальное действие выполняет код, а не сама LLM.

## Полученные навыки

AI Engineering, Tool Calling, Agent Architecture, Structured Output, проектирование инструментов, валидация AI-действий, управление состоянием, Human-in-the-Loop, обработка ошибок и AI-assisted development. Отдельно участник получает первый опыт проектирования границы полномочий AI-агента: не только «Что агент умеет?», но и «Что агенту разрешено делать самостоятельно?».

## Результат

Работающий College Event Manager Agent, который понимает естественные пользовательские команды и через ограниченный набор инструментов способен получать и изменять информацию о мероприятиях.

Минимальный рабочий цикл: `Запрос → понимание намерения → Tool Call → выполнение → результат → ответ пользователю`.

## Критерии готовности

Проект считается завершённым, если:

- агент имеет несколько специализированных инструментов;
- способен самостоятельно выбрать подходящий инструмент;
- корректно формирует аргументы вызова;
- умеет читать существующие мероприятия;
- способен создать новое событие;
- способен изменить существующее событие;
- способен отменить событие;
- изменения действительно отражаются в состоянии системы;
- при недостатке обязательной информации агент задаёт уточняющий вопрос;
- ошибки инструментов не приводят к выдуманному успешному результату;
- участник способен объяснить границу между LLM, Agent Runtime и Tool;
- участник способен показать полный жизненный цикл Tool Call.

## Demo Day

Лучше всего этот проект показывать живым диалогом. Сначала: «Что запланировано на пятницу?» — агент получает данные и отвечает. Затем: «Добавь Demo Day MINILAB на пятницу в 16:00» — агент извлекает параметры, вызывает инструмент, событие появляется в системе. После: «Перенеси его на 17:00» — состояние изменяется. И финальная проверка: «Удали Demo Day». Если реализован Safe Actions, агент останавливается: «Найден Demo Day MINILAB в пятницу в 17:00. Подтвердить отмену?». Пользователь подтверждает — только после этого выполняется действие.

На защите участник должен показать не только работающего агента, но и объяснить `LLM → Runtime → Tool → Events Data` и ответить на главный инженерный вопрос проекта: **Почему мы не дали LLM прямой доступ к данным, а заставили её работать через ограниченные инструменты?**
